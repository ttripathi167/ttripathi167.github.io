          // 07 · FLAGSHIP CASE STUDIES

          Three systems, end to end

          Depth over breadth: problem → architecture → decisions → tradeoffs → outcomes. Click a card for the full study — or hover any diagram component for detail.

          PROBLEM

          Incident responders worked across ~12 disconnected knowledge sources and 4 enterprise systems. Tribal knowledge, slow lookup, and inconsistent answers drove long time-to-resolution and real audit exposure.

          ARCHITECTURE

          ARCHITECTURE DECISIONS

          Why hybrid retrieval?

          Semantic search matched concepts well, but incident IDs, error codes, and operational terminology need exact precision — dense vectors plus BM25 cover both.

          Why reranking?

          First-pass retrieval found the right documents but ranked them inconsistently on ambiguous operational queries — a cross-encoder re-scores the top candidates before assembly.

          Why human-in-the-loop?

          High-risk actions (ticket changes, notifications, escalations) require explicit human authorization rather than autonomous execution. The gate applies to actions, not answers.

          Why MCP?

          Standardized tool contracts let agent capabilities be reused across enterprise systems instead of rebuilding one-off integrations for every workflow.

          KEY TRADEOFFS

          DecisionOption AOption BChosen
          RetrievalVector-onlyHybrid dense + BM25Hybrid — semantic match plus precision on IDs and codes.
          RankingNoneCross-encoder rerankRerank — ordering quality on ambiguous ops queries.
          Agent patternSingle agentPlanned agentic workflowAgentic — multi-system triage needs planning + tools.
          IntegrationDirect APIsMCP tool contractsMCP — reusable capabilities across 4 systems.
          ReviewFully autonomousHuman-in-the-loopHITL — humans authorize consequential actions.
          DeploymentManualIaC (Terraform)Terraform — repeatable environments, faster provisioning.

          PROBLEM

          Agents are useless without access to the systems where work happens — but every integration had its own auth, its own contract, and its own audit gaps. Point-to-point integrations don't scale with agent capabilities.

          ARCHITECTURE

          ARCHITECTURE DECISIONS

          Why MCP instead of direct APIs?

          Direct integrations multiply contracts and auth models. One MCP registry means agents learn capabilities once, and new systems plug in behind the same contract.

          Why OAuth2/OIDC + RBAC?

          Agents act with identity — every tool call carries who asked, what scope they hold, and what they're allowed to touch. API keys can't express that.

          Why least-privilege tool access?

          An agent that can read tickets shouldn't be able to close them unless the task requires it. Scopes are granted per capability, per session.

          Why REST + event-driven?

          Synchronous REST for request/response actions; events for state changes agents should react to. Each pattern where it fits — not one hammer for every nail.

          KEY TRADEOFFS

          DecisionOption AOption BChosen
          IntegrationPoint-to-point APIsMCP registryMCP — one contract, reusable across systems.
          AuthAPI keysOAuth2/OIDC + RBACOAuth2 + RBAC — identity and scopes per call.
          AccessBroad service accountLeast-privilege scopesLeast-privilege — blast radius stays small.
          PatternsSync onlyREST + event-drivenBoth — each pattern where it fits.

          OUTCOMES

          • Reusable connector catalog across 4 enterprise systems
          • Least-privilege access enforced at the gateway
          • Every tool action audit-logged

          PROBLEM

          Legal teams spent hours searching case files and summarizing documents by hand. Knowledge lived in silos; review cycles were slow and inconsistent.

          ARCHITECTURE

          ARCHITECTURE DECISIONS

          Why RAG over static models?

          The legal corpus changes with every matter. Retrieval grounds answers in current documents and produces citations — a frozen model can't do either.

          Why layout-aware parsing?

          Legal meaning lives in structure — clauses, tables, headings. Naive text splitting destroys the context that makes a passage useful.

          Why mandatory attorney review?

          High-stakes legal content is never final without a human. The system drafts and cites; attorneys decide. That boundary is architectural, not procedural.

          Why reusable components?

          Summarization, extraction, and retrieval were built once as composable components — then composed per matter type instead of rebuilt per team.

          KEY TRADEOFFS

          DecisionOption AOption BChosen
          KnowledgeFine-tuned modelRAG over live corpusRAG — current docs, with citations.
          ParsingPlain text splitLayout-aware parsingLayout-aware — structure carries meaning.
          Final outputAutonomousAttorney review gateReview gate — humans decide on high-stakes content.
          DeliveryBespoke per teamReusable componentsReusable — compose per matter, don't rebuild.

          How I design agents that survive production

          Perception

          03⚙

          Action

          06📊

          Evaluation

          Quality, groundedness, safety, cost, latency — measured continuously, gated before release.

          // 14 · ASK THE ARCHITECT

          Architectural reasoning, on record

          The questions I get in interviews — answered the way I'd whiteboard them.

          Intake first: claims arrive through an API gateway with OAuth2 identity — every request authenticated, every caller scoped. Document intelligence parses FNOL forms, photos, and PDFs into structured, chunked, embedded content.

          Orchestration: a planner decomposes the claim (validate coverage → assess damage → estimate → decide), a router picks specialist sub-agents, and all of them act through MCP tools against the claims core — never direct database access. Memory keeps claim state across the multi-day lifecycle.

          Boundaries: payout decisions above a threshold pause at a human approval gate; everything else flows. A policy engine constrains which tools each agent may call.

          Proof: an eval harness measures groundedness of summaries and correctness of extractions; latency and token budgets are enforced in CI; full trace telemetry feeds audit and regression datasets.

          Default to RAG when the corpus changes (policies, claims, legal matters), when answers need citations, and when access must be authorization-aware — retrieval naturally respects per-document permissions; a fine-tuned model's weights don't.

          Consider fine-tuning for stable, specialized behavior — tone, format, domain reasoning patterns — not for facts. And the two compose: a tuned model over a RAG pipeline.

          How I decide: prototype both against an eval dataset measuring groundedness and retrieval relevance, then choose on evidence — with hybrid dense + BM25 retrieval and reranking as the retrieval baseline to beat.

          Deterministic boundaries around non-deterministic models. Agents get capabilities through MCP tools with least-privilege scopes — an agent that reads tickets can't close them unless the task requires it.

          Layered control: a policy engine restricts which tools are callable in which states; guardrails filter inputs and outputs; human-in-the-loop gates hold consequential actions for authorization.

          Evidence: every action is audit-logged with its trace; prompt-injection and jailbreak probes run in CI; eval gates block releases that regress on safety. You don't trust agents — you constrain and verify them.

          Treat cost and latency as NFRs — budgets set up front, enforced in CI, not discovered in the invoice.

          Levers I pull: model routing (small model first, escalate on low confidence), right-sized retrieval (tight top-k, rerank only finalists), response caching for repeated queries, token budgets per request, and async/event-driven paths where immediacy isn't required.

          Proof: latency and token regression tests run on every prompt or model change — a release that blows the budget fails the build, not production.
